STORY P1-04
CONTEXT     Passkeys use your device biometric (Face ID, fingerprint) to
            log in. No password ever. The technical standard is WebAuthn.
            Key concept: your device generates a key pair. The private key
            never leaves your device. The public key goes to the server.
            When you log in your device signs a challenge with the private
            key. The server verifies with the public key. Even if the server
            database is stolen there is nothing to use for login.
            Fido2NetLib is the .NET library handling the WebAuthn ceremony.
            NEW CONCEPT: entirely new. Budget a full weekend. Ask Claude
            to explain the full WebAuthn flow before writing any code.
TASK        Build passkey registration and login via WebAuthn
CRITERIA    Fido2NetLib NuGet package installed
            POST /api/auth/passkey/register/options returns challenge
            Challenge stored server-side for verification
            POST /api/auth/passkey/register/verify stores public key
            Public key saved in PasskeyCredentials linked to user
            POST /api/auth/passkey/login/options returns challenge
            POST /api/auth/passkey/login/verify validates signature
            Valid signature: issues JWT + refresh token
            Tested working on iOS Safari with Face ID
            Tested working on Android Chrome with fingerprint
            Magic link always available as fallback
DONE WHEN   Returning user authenticates with device biometric and receives
            valid JWT without typing any credentials
DEPENDS ON  P1-03
ESTIMATE    8h
TESTED BY   Manual on real device — emulators do not have biometrics
WEEK        May 26

STORY P1-05
CONTEXT     JWT (JSON Web Token): a string containing encoded user info
            (claims) and a cryptographic signature. The server creates it
            at login and the client sends it with every request as proof
            of identity. Short expiry (15 mins) for security.
            Refresh token: longer-lived token (30 days) that gets you a
            new JWT without logging in again. Together they give security
            of short-lived tokens with convenience of staying logged in.
TASK        Build JWT issuance and refresh token flow
CRITERIA    JWT contains claims: UserId, Username, ProfileComplete
            JWT expiry 15 minutes
            Refresh token is a cryptographically secure 64-byte random string
            Refresh token stored in RefreshTokens with 30 day expiry
            POST /api/auth/refresh accepts refresh token, returns new JWT
            Used refresh token invalidated immediately after use
            New refresh token issued alongside new JWT on each refresh
            POST /api/auth/logout invalidates the refresh token in DB
            Expired JWT returns 401 on all protected routes
DONE WHEN   JWT expires after 15 mins, refresh request issues new JWT,
            old refresh token cannot be reused
DEPENDS ON  P1-03
ESTIMATE    4h
TESTED BY   Manual flow test + integration test in P1-14
